\section{Introducci\'on}

El presente documento define la forma en que se organizar\'a, ejecutar\'a y
controlar\'a el proyecto \proyectoNombre{} (\proyectoNombreLargo). Su objetivo
es establecer las responsabilidades del equipo, la metodolog\'ia de trabajo,
los mecanismos de seguimiento y las herramientas que se utilizar\'an durante
el desarrollo.

Este documento describe la gesti\'on general del proyecto. Los requerimientos
funcionales y no funcionales se mantienen en su documento correspondiente,
mientras que cada sprint contar\'a con un Plan de Iteraci\'on y un Gantt
espec\'ificos.

El backlog y el estado operativo de las tareas se mantendr\'an en Jira. De esta
forma se evita duplicar informaci\'on que cambia frecuentemente dentro de los
documentos formales del proyecto.

\section{Metodolog\'ia de trabajo}

El proyecto se desarrollar\'a mediante un marco de trabajo \'agil basado en
Scrum, organizado en sprints de dos semanas. Cada sprint tendr\'a un objetivo
concreto y un conjunto de tareas seleccionadas de acuerdo con las prioridades
del proyecto y la capacidad disponible del equipo.

Al inicio de cada sprint se elaborar\'an dos artefactos:

\begin{itemize}
  \item Un Plan de Iteraci\'on con el objetivo, alcance, tareas,
        responsables y entregables comprometidos.
  \item Un Gantt de Iteraci\'on con la distribuci\'on temporal de las tareas,
        sus dependencias y los hitos correspondientes.
\end{itemize}

\subsection{Gesti\'on del backlog}

Jira ser\'a la fuente oficial para la administraci\'on del backlog. Cada tarea
deber\'a incluir, cuando corresponda:

\begin{itemize}
  \item Una descripci\'on clara del trabajo.
  \item Un responsable.
  \item Una prioridad.
  \item Una estimaci\'on de esfuerzo.
  \item Una fecha objetivo.
  \item Criterios de aceptaci\'on.
  \item Dependencias o bloqueos conocidos.
  \item Evidencia del resultado obtenido.
\end{itemize}

Las tareas se priorizar\'an considerando:

\begin{enumerate}
  \item Su importancia para el MVP.
  \item Las dependencias t\'ecnicas o documentales.
  \item Los compromisos acad\'emicos.
  \item El riesgo que permitan reducir.
  \item La capacidad disponible del equipo.
\end{enumerate}

El esfuerzo se estimar\'a inicialmente en horas de trabajo. Al cierre de cada
sprint se comparar\'a el esfuerzo estimado con el esfuerzo real para mejorar
la planificaci\'on de las siguientes iteraciones.

\subsection{Criterios de preparaci\'on y terminado}

Una tarea se considerar\'a preparada para ingresar a un sprint cuando:

\begin{itemize}
  \item Su objetivo y alcance sean comprensibles.
  \item Tenga un responsable identificado.
  \item Sus dependencias principales sean conocidas.
  \item Cuente con una estimaci\'on inicial.
  \item Tenga criterios de aceptaci\'on verificables.
\end{itemize}

Una tarea se considerar\'a terminada cuando:

\begin{itemize}
  \item El trabajo comprometido haya sido completado.
  \item Cumpla sus criterios de aceptaci\'on.
  \item Haya sido revisada por al menos otro integrante cuando corresponda.
  \item Las pruebas necesarias hayan sido ejecutadas.
  \item El c\'odigo o documento resultante se encuentre versionado.
  \item El issue de Jira incluya evidencia o un enlace al resultado.
  \item No existan errores o bloqueos conocidos que impidan utilizar el
        entregable.
\end{itemize}

\section{Planificaci\'on y seguimiento}

La planificaci\'on general de LEIP se organizar\'a progresivamente alrededor de
las siguientes etapas:

\begin{enumerate}
  \item Definici\'on del producto y sus requerimientos.
  \item Dise\~no de la arquitectura y del modelo de datos.
  \item Implementaci\'on del sistema de extracci\'on y procesamiento.
  \item Implementaci\'on de la capa de inteligencia econ\'omica.
  \item Desarrollo de la API y de la aplicaci\'on web.
  \item Integraci\'on, validaci\'on, despliegue y documentaci\'on final.
\end{enumerate}

Estas etapas no se consideran fases completamente aisladas. Podr\'an
desarrollarse de manera incremental y superponerse cuando las dependencias
t\'ecnicas lo permitan.

El avance se controlar\'a mediante los tableros, sprints e issues registrados
en Jira. Durante las reuniones semanales se revisar\'an:

\begin{itemize}
  \item Las tareas completadas.
  \item Las tareas en curso.
  \item Los bloqueos existentes.
  \item Las desviaciones respecto al Plan de Iteraci\'on.
  \item Las decisiones necesarias.
  \item Los riesgos nuevos o modificados.
\end{itemize}

Los cambios que afecten el alcance del MVP, los requerimientos o la arquitectura
deber\'an registrarse y evaluarse antes de ser incorporados al backlog. La
evaluaci\'on considerar\'a su valor, costo, riesgo e impacto sobre el cronograma.

Los riesgos detallados del proyecto se mantendr\'an en el documento de Lista de
Riesgos. Cuando un riesgo requiera una acci\'on concreta, esta se registrar\'a
también como tarea en Jira.

realizar\'an mediante las siguientes herramientas:

\begin{table}[htbp]

\begin{tabularx}{\textwidth}{@{}p{3.8cm} X@{}}
\toprule
\textbf{Herramienta} & \textbf{Uso} \\
\midrule
Jira &
Gesti\'on del backlog, planificaci\'on de sprints, asignaci\'on de
responsables, seguimiento de tareas y registro del avance. \\

Microsoft Teams &
Comunicaci\'on del equipo y realizaci\'on de videollamadas internas y con el

GitHub &
Control de versiones del c\'odigo fuente, documentaci\'on t\'ecnica y
artefactos formales del proyecto. \\

LaTeX &
Elaboraci\'on y mantenimiento de la documentaci\'on acad\'emica y t\'ecnica. \\
\bottomrule
\end{tabularx}
\end{table}

Las grabaciones, transcripciones y res\'umenes autom\'aticos se conservar\'an
inicialmente en Microsoft Teams. Las decisiones relevantes y las tareas
resultantes se revisar\'an antes de considerarse definitivas.

La informaci\'on producida durante una reuni\'on se procesar\'a de la siguiente
forma:

\begin{enumerate}
  \item Realizaci\'on y, cuando corresponda, grabaci\'on de la reuni\'on.
  \item Generaci\'on de la transcripci\'on y el resumen.
  \item Revisi\'on del resumen por un integrante del equipo.
  \item Registro de las decisiones relevantes.
  \item Creaci\'on o actualizaci\'on de las tareas correspondientes en Jira.
  \item Incorporaci\'on de la documentaci\'on definitiva al repositorio
        cuando deba conservarse como evidencia del proyecto.
\end{enumerate}

Cada minuta deber\'a identificar, como m\'inimo:

\begin{itemize}
  \item La fecha de la reuni\'on.
  \item Los participantes.
  \item Los temas tratados.
  \item Las decisiones adoptadas.
  \item Las tareas resultantes.
  \item Los responsables y fechas acordadas.
\end{itemize}

\section{Criterios de finalizaci\'on y aceptaci\'on}

Un sprint se considerar\'a finalizado cuando:

\begin{itemize}
  \item Se haya realizado la revisi\'on de la iteraci\'on.
  \item Los entregables completados se encuentren disponibles.
  \item El estado de las tareas est\'e actualizado en Jira.
  \item Las tareas no terminadas hayan sido replanificadas.
  \item Los bloqueos, decisiones y aprendizajes hayan sido registrados.
\end{itemize}

El proyecto se considerar\'a finalizado cuando:

\begin{itemize}
  \item Los requerimientos prioritarios del MVP hayan sido implementados y
        verificados.
  \item El sistema permita extraer, validar, almacenar y consultar la
        informaci\'on econ\'omica definida para el MVP.
  \item La trazabilidad de los datos se mantenga desde la fuente original
        hasta su presentaci\'on.
  \item Las m\'etricas de inteligencia econ\'omica comprometidas hayan sido
        implementadas y validadas.
  \item La API y la aplicaci\'on web permitan acceder correctamente a la
        informaci\'on.
  \item Las pruebas necesarias hayan sido ejecutadas.
  \item La documentaci\'on acad\'emica y t\'ecnica se encuentre completa.
  \item La versi\'on final del producto pueda ser desplegada y demostrada.
  \item El equipo y el tutor acepten los entregables correspondientes.
\end{itemize}
